# 风电场三维数字孪生 DEMO 产品级视觉与交互全面重构提示词

## 一、项目背景与改造目标

你是一名资深工业软件产品设计师、数字孪生可视化专家、CesiumJS 三维开发工程师和前端架构师。

请全面检查并改造以下项目：

GitHub 仓库：https://github.com/hiterls1992/wind-farm-digital-twin

项目名称：凉城 60 MW 陆上风电项目三维数字孪生 DEMO。

现有技术基础：

- 三维引擎：CesiumJS 1.118，已本地化。
- 前端：原生 HTML、CSS、JavaScript，无构建工具。
- 数据处理：Python。
- 空间数据：CGCS2000 高斯投影实测机位坐标、经纬度、实测高程、DEM 地形数据。
- 已有功能：三维地形、风机机位展示、多底图源、机位数据看板及相关数据处理功能。
- 项目用途：风电项目前期向业主展示项目场址、机位布局、地形地貌和项目建设条件，辅助方案沟通及项目汇报。

本次改造的重点不是增加大量功能，而是**全面改善现有 DEMO 的视觉品质、信息层级、三维场景表现、操作逻辑和业主汇报体验**。

请直接在现有仓库基础上实施代码修改，而不是只给设计建议、静态效果图或者一份开发计划。

### 1.1 必须解决的问题

重点解决以下问题：

1. 界面元素过多，视觉焦点不明确，用户不知道首先应该看哪里。
2. 三维地形和风机机位没有充分成为页面主体，界面与场景争夺注意力。
3. 关键指标、项目基本信息、机位数据和技术参数之间缺乏清晰的信息层级。
4. 面板、按钮、卡片、文字、图表的样式缺乏统一设计语言。
5. 操作入口分散，功能组织方式不够直观。
6. 初次打开页面时，无法快速理解项目规模、场址位置和风机布局。
7. 缺少面向业主汇报的叙事性，现有功能更像开发调试界面，而不是成熟的展示产品。
8. 不同屏幕分辨率下，三维场景和数据面板之间可能存在布局冲突。
9. 地形、风机、底图和数据加载过程缺少完善的视觉反馈与异常处理。

以上是改造目标，不要在未经检查实际代码之前就认定每一项问题都已经存在。请先验证现状，再按实际情况实施。

## 二、总体产品定位

### 2.1 产品定位

将现有 DEMO 升级为：

**面向风电项目前期方案汇报的三维数字孪生可视化展示平台。**

它首先是一款用于项目沟通和方案展示的工具，其次才是数据查询工具。

设计必须遵循以下优先级：

1. 让业主第一眼感受到场址地形与风场布局的空间真实性。
2. 让业主快速了解项目规模、机位数量、装机容量和主要场址特征。
3. 让业主能够直观查看各台风机的空间位置及相关数据。
4. 让汇报人员可以流畅地切换全场、局部和单机视角。
5. 保留工程数据的真实性与技术可信度。
6. 方便后续扩展道路、集电线路、升压站、施工区域及其他工程要素。

### 2.2 设计原则

- 场景优先：三维场景是核心展示区域，UI 只承担辅助说明功能。
- 重点突出：每个页面只设置一个主要视觉焦点。
- 渐进披露：先展示项目摘要，再展示详细数据，避免一次呈现全部信息。
- 数据真实：已有实测数据优先，模拟数据必须明确标识。
- 统一规范：所有卡片、按钮、文字、图表和交互状态遵循统一设计系统。
- 工程可信：不为了视觉效果牺牲坐标精度、地形关系和机位实际位置。
- 操作克制：减少装饰性控件，常用操作应当容易发现。
- 性能优先：视觉优化不能导致三维场景卡顿、加载缓慢或内存持续增长。
- 渐进重构：优先重用现有技术栈，确有必要时再调整架构。

## 四、第二阶段：重新设计整体信息架构

### 4.1 页面结构

将主界面组织为以下四个逻辑区域：

1. 顶部：项目身份、项目名称和少量全局操作。
2. 中央：大面积三维场景。
3. 侧边：项目摘要、机位信息及按需展开的分析面板。
4. 底部：轻量级场景控制、图例及必要的状态提示。

不要将四个区域设计成四块面积相近、互相竞争的独立面板。

建议采用：

- 中央三维场景占据可用视口的约 75%～85%。
- 左右信息面板默认采用收敛的宽度。
- 非核心面板可以折叠、隐藏或通过按钮展开。
- 场景在面板开关时应平滑适配，而不是被面板永久遮挡。
- 机位详情优先采用侧边抽屉或轻量信息卡，不要默认常驻一个庞大的详情表。

以上比例为设计目标，应根据实际屏幕、现有 Cesium 容器和文字长度调整。

### 4.2 顶部导航

重新设计顶部区域。

左侧：

- 项目名称：凉城 60 MW 陆上风电项目。
- 产品标识：风电场数字孪生。
- 必要时显示项目所在地的简短说明。

中部或次级区域：

- 场址总览。
- 机位分析。
- 地形分析。
- 工程要素。

这些入口只在对应功能真实存在或已经完成实现时展示。尚未实现的模块不能以已完成产品的形式呈现。

右侧：

- 场景复位。
- 全屏切换。
- 图层设置。
- 必要的帮助或演示模式入口。

要求：

- 不使用传统后台管理系统的多级菜单风格。
- 避免大面积 Logo、冗余标题和无意义装饰。
- 不要在顶部堆叠所有技术参数。
- 顶部应轻薄、稳定、不遮挡三维场景。

### 4.3 信息展示分级

按照三个层级组织数据。

**一级：项目概览**

用于初次打开和业主汇报：

- 项目名称。
- 项目所在地。
- 装机容量。
- 风机台数。
- 场址海拔范围或地形概况。
- 数据来源或数据可信度说明。

只展示现有数据能够支持的指标。不能计算或确认的数据应隐藏，而不是填入虚构值。

**二级：场址分析**

在用户需要深入了解时展示：

- 风机编号。
- 机位空间位置。
- 实测高程。
- 风速及已有发电量指标。
- 机位之间的空间关系。
- 已实现的地形和机位分析结果。

**三级：工程技术信息**

通过详情面板、折叠区域或调试模式展示：

- CGCS2000 坐标。
- 经纬度。
- 投影带号及中央子午线等坐标信息。
- 数据来源。
- DEM 高程与实测高程差异。
- 数据处理状态和必要的技术诊断信息。

不要把三级技术信息全部放在主展示界面中。技术信息应当可以查询，但不能成为业主首先看到的内容。

## 五、第三阶段：建立统一视觉设计系统

### 5.1 主视觉风格

采用：

**现代工业科技感 + 高品质地理信息可视化 + 克制的数字孪生风格。**

整体应当显得专业、清晰、可信，适合在会议室大屏、投影仪和普通办公电脑上进行演示。

避免：

- 过度使用荧光蓝。
- 黑底上堆叠大量发光边框。
- 大量旋转、闪烁的装饰动画。
- 玻璃拟态导致的文字对比度不足。
- 无意义的经纬网、雷达扫描线和科技纹理。
- 每个数字都做成独立的大型仪表盘。
- 过度密集的网格背景。
- 卡片边框层层叠加。
- 为了追求科技感而使用难以阅读的小字号。

### 5.2 配色规范

建立统一的 CSS 变量，不允许每个组件自行定义一套颜色。

建议基础色板：

- 页面与顶栏：深石墨蓝或深海军蓝。
- 面板：比背景略亮的深蓝灰。
- 主强调色：清晰、明亮的青蓝色。
- 次强调色：适度的蓝绿色。
- 主要文字：接近白色的浅灰。
- 次级文字：中灰蓝。
- 分隔线：低对比度的蓝灰色。
- 正常状态：绿色。
- 注意状态：琥珀色。
- 异常状态：红色。

要求：

1. 主色只用于重要按钮、选中机位、关键数据和必要的交互反馈。
2. 状态颜色必须具有明确含义，不能仅作为装饰。
3. 地形色带与机位状态色需要区分，避免同一种颜色表达两个不同含义。
4. 图表应采用有限的颜色序列。
5. 保证投影显示时的文字可读性。
6. 将颜色统一定义在 CSS Variables 中，便于后续切换主题。

### 5.3 字体和排版

- 中文优先使用 Microsoft YaHei、系统中文无衬线字体。
- 数字可以使用适合工程数据展示的无衬线字体。
- 项目标题、模块标题、指标值、标签、辅助说明分别建立字号层级。
- 关键指标使用清晰、稳定的数字排版。
- 不要使用过小的字号显示坐标和说明。
- 长标题应当合理换行或省略，并提供必要的完整内容查看方式。
- 统一文字颜色、字重、行高和组件内边距。

### 5.4 组件规范

建立统一组件样式：

- 主按钮、次按钮、图标按钮。
- 普通卡片、指标卡片。
- 标签、状态标识。
- 侧边抽屉。
- 下拉菜单。
- 提示框。
- 图例。
- 图表容器。
- 空数据状态。
- 加载状态。
- 错误提示。
- 确认和反馈信息。

统一规定：

- 圆角大小。
- 边框样式。
- 阴影强度。
- 组件间距。
- 按钮高度。
- 悬停、选中、禁用状态。
- 动画时长。
- 焦点和键盘交互状态。

优先复用项目现有技术方案，不为简单的卡片或按钮额外引入大型 UI 框架。

## 六、第四阶段：重点优化 Cesium 三维场景

这是整个项目改造的核心。三维场景的表现效果应当优先于外围 UI 的装饰性优化。

### 6.1 初始视角与场景构图

重新设计页面首次打开时的默认视角。

要求：

1. 能够完整呈现风场主要地形和全部风机机位。
2. 让机位分布清晰可辨，同时保留地形起伏的整体印象。
3. 不应过度俯视导致地形失去立体感。
4. 不应过度倾斜导致远端机位被地形遮挡。
5. 避免镜头距离过远，使风机变成无法辨认的小点。
6. 避免镜头距离过近，导致场址范围无法完整呈现。
7. 根据实际机位坐标计算合理的包围范围和观察位置。
8. 提供一键恢复到推荐汇报视角的功能。

如果机位数量、空间范围或地形范围发生变化，默认视角应尽量根据实际数据自动适配，不要写死仅适用于当前 DEMO 的相机参数。

### 6.2 地形表现

优化地形的可读性和空间层次：

- 保留真实地形数据与已有高程关系。
- 根据现有数据和引擎能力，改善地形明暗、色彩和视觉层次。
- 让山脊、沟谷、坡地等主要地貌特征更容易识别。
- 在适当情况下使用自然地形色带，而不是完全依赖单一颜色。
- 根据显示模式控制地形色带、影像底图和必要的边界叠加。
- 优化远景和近景的视觉关系。
- 避免过度提高垂直夸张度，造成虚假的地貌认知。
- 提供适度的光照和阴影表现，但不能让阴影掩盖风机和地形细节。

如果现有地形数据精度不足，应如实展示其能力边界，不得通过渲染效果暗示不存在的精度。

### 6.3 风机模型与机位标识

逐台检查风机实体的显示效果。

要求：

- 风机应当在合理观察距离下具有清晰的辨识度。
- 风机模型的尺寸、塔筒比例和叶轮形态应尽可能协调。
- 风机在场景中的高度和位置必须与原始工程数据保持一致。
- 风机的颜色应当与地形背景有足够的对比度。
- 正常机位使用统一的视觉语言。
- 当前选中机位具有明显但不过度刺眼的高亮效果。
- 鼠标悬停时提供轻量反馈。
- 选中机位时展示编号及必要的关键指标。
- 不要让全部风机永久显示大量文字标签。

建议建立三种显示状态：

1. 全场浏览：显示简洁的机位编号或轻量标识。
2. 机位分析：显示更多机位标签，并允许突出特定机位。
3. 单机详情：突出目标风机，其余机位适当弱化。

标签应考虑遮挡、重叠、远近景缩放和显示密度。若使用 Cesium 标签实体，应根据现有代码选择合适的距离显示条件、深度测试和缩放策略。

### 6.4 机位交互

完善以下交互流程：

- 单击风机：选中该机位。
- 选中后：展示机位编号和核心信息。
- 双击或明确的详情操作：进入单机查看视角。
- 详情面板中：显示已有的机位数据。
- 点击其他机位：切换选中对象和详情内容。
- 点击场景空白区域：按照合理的交互规则取消选择。
- 点击场景复位：返回全场视角。
- 关闭详情面板：恢复主要场景展示空间。

具体鼠标事件必须避免互相冲突，尤其是 Cesium 的点击、双击、拖动、滚轮缩放和默认相机控制。

不要因为选中一个机位就意外触发相机飞行，也不要让双击机位的行为与普通点击详情产生重复执行。

### 6.5 图层控制

将分散的场景设置整合为简洁的图层控制面板。

根据现有功能，考虑包含：

- 卫星影像或其他现有底图。
- 地形显示。
- 风机机位。
- 机位编号。
- 已实现的边界、道路或其他工程要素。

尚未实现的图层不能仅添加一个无效开关。

要求：

- 图层名称使用工程人员和业主都能理解的语言。
- 提供清楚的开关状态。
- 图层切换时及时反馈。
- 不同图层应保持合理的叠加顺序。
- 切换底图不应造成风机位置改变。
- 关闭图层后应释放不再需要的资源，或按实际情况进行合理管理。

### 6.6 相机与场景控制

建立简洁、易理解的场景操作：

- 全场。
- 顶视。
- 适度倾斜的三维视角。
- 场景复位。
- 全屏。
- 必要的放大、缩小及图层控制。

如果提供视角预设，预设名称应当明确。

不要将大量相机操作按钮永久放在页面上。低频操作可放入折叠菜单或悬浮控制组。

所有相机动画都必须具备合理的时间和结束状态，不应产生连续重复的飞行动画或无法取消的操作。

## 七、第五阶段：重新设计业主展示面板

### 7.1 项目概览面板

首次打开页面时，显示一个简洁的项目摘要。

推荐结构：

顶部：项目名称和场址。

核心指标区：

- 装机容量。
- 风机台数。
- 其他经过核实且适合前期展示的指标。

辅助信息区：

- 场址位置。
- 地形概况。
- 数据来源说明。

要求：

- 不要把所有指标都做成同等大小的卡片。
- 只将最重要的两到四项指标作为视觉重点。
- 其他信息使用较轻量的文本和标签。
- 项目名称与三维场景应当保持主次关系。
- 面板能够收起，避免遮挡地形和机位。

### 7.2 单台风机详情面板

单击机位后，打开轻量级详情面板。

建议包含：

- 机位编号。
- 实测高程。
- 实测风速。
- 已有的理论发电量、上网电量和等效小时等指标。
- 坐标及经纬度。
- 其他已有的、经过确认的数据。

分成两组：

**关键指标：** 用户最需要理解的数值。

**工程详情：** 坐标、数据来源和其他技术信息。

要求：

1. 不显示空值、`undefined`、`NaN` 或错误的单位。
2. 单位必须完整、准确。
3. 小数位数遵循工程数据的实际精度。
4. 不能将理论值描述成实测值。
5. 不能将模拟值描述成实时监测值。
6. 没有的数据不应通过随机生成补齐。
7. 切换机位时，面板内容必须与当前选中对象同步。

### 7.3 指标图表

对已有且具有展示价值的数据，考虑使用简洁的图表。

可以根据现有数据选择：

- 风机指标横向比较。
- 各机位高程对比。
- 各机位风速对比。
- 现有发电量指标对比。
- 其他具备实际分析意义的内容。

不要求全部实现。应当根据真实数据的意义选择最合适的图表。

要求：

- 图表有明确标题、单位和数据范围。
- 图表不应占据主场景的主要空间。
- 默认不同时展开多个复杂图表。
- 图表中的数据必须来自现有数据源。
- 不得通过编造时间序列或随机数制造实时监测效果。
- 机位数量较少时，优先采用清晰的柱状图或排序列表，而不是复杂的仪表盘。
- 图表与三维场景中的机位选择保持联动；若实现联动，应验证双向状态同步。

### 7.4 状态和数据说明

当前项目是前期展示 DEMO，必须明确区分：

- 工程实测数据。
- 根据工程资料计算的数据。
- DEM 或外部地理服务数据。
- 演示模拟数据。
- 当前未接入的数据。

如果项目尚未连接真实 SCADA 或实时气象系统，不得显示“实时功率”“实时风速”“在线监控”等容易让业主误解的表述。

如有必要，在页面角落设置简洁的数据来源说明，避免大面积免责声明影响展示。

## 八、第六阶段：增加面向业主汇报的演示模式

这是本次改造的重要加分项。

在不影响普通交互的前提下，设计一个独立的“演示模式”或“汇报模式”。

### 8.1 演示模式目标

用户开启后，页面自动切换为更适合会议室投影的展示布局：

- 收起非必要的控制面板。
- 保留项目名称。
- 突出三维场景。
- 显示少量核心项目指标。
- 提供明确的场景切换入口。
- 尽量减少技术调试信息。
- 提高大屏上的文字和数据可读性。

演示模式必须能够随时退出，并恢复正常浏览模式。

### 8.2 建议的演示流程

设计以下场景切换顺序：

**场景一：项目总览**

展示完整风场、主要地形和全部机位。

**场景二：场址与地形**

适当调整观察角度，突出地形起伏、场址空间关系及已有的地形分析内容。

**场景三：机位分布**

突出风机编号、整体布局和机位之间的空间关系。

**场景四：典型机位**

选择一台风机，展示其空间位置、高程、风速及其他已有指标。

**场景五：回到全场**

恢复全场视角，结束展示。

要求：

- 只有真实可用的场景才能出现在演示流程中。
- 场景切换应当平滑，但不能过度动画化。
- 每个场景只突出少量核心信息。
- 支持手动切换，不能强制用户等待动画。
- 如果实现自动播放，应提供暂停、继续和退出操作。
- 不得在用户交互时强制继续播放相机动画。
- 不应将演示模式设计成独立于主系统的重复页面。

### 8.3 演示过程的可靠性

演示模式不能依赖不可控的网络数据或临时生成的内容。

对于需要联网加载的卫星影像：

- 提供加载状态。
- 失败时显示明确提示。
- 不能让整个演示页面无限等待。
- 在可行情况下，保留可用的地形或基础场景。

如果需要离线演示，应当在项目现有资源和许可允许的前提下实现，不要未经检查就复制或打包大量外部影像。

## 九、第七阶段：改善操作逻辑与交互反馈

### 9.1 统一交互规则

全站交互应当具有一致性：

- 悬停：轻量反馈。
- 点击：明确状态变化。
- 选中：持续可识别。
- 禁用：明确不可操作。
- 加载：显示进度或状态。
- 错误：提供可理解的原因和恢复方式。
- 完成：及时反馈结果。

不要让不同面板对相同按钮采用完全不同的交互规则。

### 9.2 消除无效控件

全面检查所有按钮、菜单、图层开关、标签和导航入口。

要求：

- 每个可点击控件都必须实现对应功能。
- 不存在无效的按钮和空操作。
- 不存在点击后没有反馈的交互。
- 不存在只有装饰作用、却看起来可以点击的控件。
- 不存在重复的功能入口。
- 不存在无法关闭的弹窗或抽屉。

如果某项功能暂时无法实现，应当从正式展示界面中移除，而不是保留一个无效按钮。

### 9.3 键盘和鼠标操作

至少检查：

- 鼠标拖动旋转。
- 滚轮缩放。
- 机位点击。
- 双击操作。
- 图层切换。
- 面板展开和收起。
- 全屏和退出全屏。
- Esc 关闭弹层或退出适当的交互状态。
- 键盘焦点和按钮可访问性。

不要破坏 Cesium 默认相机控制。必要时应通过统一的交互管理逻辑协调事件。

### 9.4 动画规范

动画只用于帮助用户理解状态变化。

建议：

- 面板展开和收起：短时、平滑。
- 机位选中：轻量高亮。
- 相机飞行：合理时长。
- 数据加载：明确的加载反馈。
- 数字变化：仅在数据确实变化且具有意义时使用。

避免无限循环的装饰动画、持续闪烁的边框和无意义的数字滚动。

尊重系统的减少动态效果设置。

## 十、第八阶段：响应式布局与大屏适配

本项目主要面向桌面端，但应考虑不同的办公显示器和会议室投影设备。

至少验证以下场景：

- 1920 × 1080。
- 1600 × 900。
- 1366 × 768。
- 常见 16:9 大屏全屏展示。
- 浏览器窗口缩放和尺寸变化。

要求：

1. 三维场景始终填满可用展示区域。
2. 面板不能覆盖关键机位。
3. 窄屏下应自动收起次要面板。
4. 文字不能因为固定高度被裁切。
5. 指标卡片应根据空间变化调整排列。
6. 图表在不同宽度下仍然可读。
7. 全屏切换前后应正确刷新 Cesium 场景尺寸。
8. 页面缩放后，鼠标交互位置必须与视觉对象保持一致。
9. 不能出现水平滚动条或大面积空白区域。
10. 不应使用大量固定像素定位来维持单一分辨率下的布局。

如果项目目前只支持桌面浏览，应优先做好桌面端，而不是为了追求全面适配牺牲大屏效果。

## 十一、第九阶段：代码架构与工程质量

本项目当前采用原生 JavaScript、CesiumJS 和 Python 数据处理。此次改造应优先保持原有技术栈。

### 11.1 代码组织

根据实际代码情况，适当拆分以下职责：

- 页面初始化。
- UI 布局和组件。
- 主题与样式。
- Cesium 场景初始化。
- 机位实体管理。
- 机位选中与详情状态。
- 图层管理。
- 相机视角管理。
- 演示模式。
- 数据读取和格式化。
- 错误处理。
- 性能诊断。

如果现有架构已具备清晰的模块划分，应当在现有结构上优化，不要为了形式上的模块化而大规模重写。

### 11.2 状态管理

统一管理：

- 当前选中的机位。
- 当前展示模式。
- 当前打开的面板。
- 当前底图。
- 当前图层可见性。
- 当前相机预设。
- 演示模式状态。
- 数据加载状态。

同一个状态不能在多个模块中各自保存一份互不关联的值。

尤其要避免：

- 场景选中状态与详情面板不一致。
- 图层按钮显示开启，但图层实际已关闭。
- 退出演示模式后面板状态异常。
- 相机复位后仍保留错误的机位高亮。
- 多次切换场景后重复注册事件。

### 11.3 Cesium 资源管理

重点检查：

- 是否重复创建 Viewer。
- 是否重复注册事件监听器。
- 是否不断重复添加相同的实体。
- 是否在重复渲染时遗留旧的标签和图层。
- 是否在不再使用时正确清理定时任务、事件监听器及临时资源。
- 是否合理使用 Entity、Primitive、DataSource 和其他现有对象。
- 是否存在大量无必要的 DOM 更新。
- 是否在每一帧中执行不必要的数据计算。

不要求盲目使用 Primitive 替代 Entity，应根据实际机位规模、标签复杂度、交互要求和测试结果决定。

### 11.4 依赖管理

- 优先使用项目已经本地化的 CesiumJS。
- 不要随意升级 CesiumJS 版本。
- 不要引入庞大的前端框架来完成简单 UI。
- 新增第三方依赖必须说明必要性。
- 不得覆盖或删除项目现有的重要资源。
- 不得依赖未经验证的 CDN 资源才能启动核心展示。
- 不得引入未经许可的地形、影像或模型资源。

### 11.5 代码可维护性

- 消除重复的 CSS 规则。
- 统一命名。
- 减少全局变量污染。
- 避免通过字符串拼接构建复杂 HTML。
- 正确处理用户输入和数据内容。
- 不要把所有功能都写在一个巨大函数里。
- 对关键坐标处理和状态管理逻辑保留必要注释。
- 不要为了让代码看起来更简洁而删除必要的工程校验。

## 十二、第十阶段：性能、加载和异常处理

### 12.1 加载体验

页面应当具有清晰的初始化过程：

1. 页面框架加载。
2. Cesium 引擎初始化。
3. 基础场景建立。
4. 地形与底图加载。
5. 风机机位加载。
6. 项目数据与面板就绪。

不要求将内部技术步骤全部显示给业主，但需要为用户提供明确、合理的加载反馈。

### 12.2 性能优化

重点排查：

- 重复创建实体。
- 过多的 DOM 节点。
- 高频重绘。
- 无效动画。
- 图表重复初始化。
- 地形与影像资源加载过重。
- 重复解析数据。
- 事件监听器泄漏。
- 全屏或窗口缩放后的重复计算。
- 面板开关导致的 Cesium 场景异常刷新。

如果增加机位标签、图层或者图表，应评估对性能的实际影响。

### 12.3 异常处理

至少处理：

- Cesium 初始化失败。
- 地形数据加载失败。
- 卫星影像不可用。
- 机位数据缺失。
- 数据格式异常。
- 某些指标为空。
- 窗口缩放异常。
- 全屏操作失败。
- 单机详情缺少字段。

要求：

- 不得出现未捕获的关键 JavaScript 异常。
- 网络资源失败不能导致所有 UI 无法使用。
- 对业主展示界面，不暴露大段技术堆栈。
- 技术错误可以记录到控制台或诊断日志。
- 错误提示应明确指出受影响的功能。
- 在不影响数据真实性的前提下提供合理的降级展示。

## 十三、第十一阶段：测试与验收

不能以“页面能够打开”作为完成标准。

- 页面正常启动。
- 三维场景正确显示。
- 风机机位数量和空间位置正确。

- 全屏与退出全屏正常。

- 窗口尺寸变化后场景正常。
- 网络异常时提供合理提示。
- 所有可点击控件均有实际作用。

使用实际浏览器启动项目，检查至少三个分辨率。

重点检查：

- 第一屏是否有清晰的视觉焦点。
- 三维场景是否真正成为主体。
- 风机和地形是否容易辨认。
- 项目指标是否简洁、清晰。
- 面板是否遮挡重要机位。
- 文字是否存在截断、重叠或对比度不足。
- 不同组件的圆角、间距和颜色是否统一。
- 页面是否仍有大量无效按钮或装饰。
- 演示模式是否适合会议室投影。
- 关键交互是否能在合理时间内完成。

如果具备浏览器自动化工具，优先使用自动化测试和截图对比；如果只能人工测试，应实际启动浏览器逐项验证，不得声称执行了未执行的测试。

### 13.3 工程数据回归

使用改造前后的同一份输入数据进行对照。

至少确认：

- 风机编号不变。
- 风机数量不变。
- 原始坐标不变。
- 转换后经纬度与原计算结果一致。
- 实测高程不变。
- 机位间相对位置关系不变。
- 原有指标的数值和单位不变。
- 数据缺失时没有被虚构数据覆盖。

UI 的数值格式可以调整，但底层工程数值不能因此发生变化。

1. 修改后的全部代码。
2. `docs/UI_REDESIGN_AUDIT.md`。
3. `docs/UI_REDESIGN_CHANGELOG.md`。
4. 更新后的 README，说明启动方式及演示模式操作方法。
5. 功能测试结果。
6. 工程数据回归结果。
7. 视觉验收截图或可验证的运行效果。
8. 已知问题与下一阶段建议。

如果某项测试未能执行，明确说明原因，不得虚构测试通过结果。
